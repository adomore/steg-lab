# 使用工具而不被工具误导

本仓库里每一个解析器都对着一个外部工具做过交叉验证——pngcheck、djpeg、tshark、ffmpeg、
mtools、debugfs、ntfscat。这么做产出了第二个计划外的结果：**一份「每个工具的输出会在哪里
被读错」的清单**。这份文档就是那份清单。

它不是工具教程。手册讲的是怎么调用。下面写的是手册不说、而在本仓库自己的载体上量出来的东西。

## 唯一的规则

**工具的沉默不是「不存在」的证据，工具的输出也不是「存在」的证据。** 两个方向都需要一个在
同源干净载体上实测的基线，任何东西才能到 E3——这与证据阶梯对本仓库自家检测器的要求是同一条。
**工具不因为是别人写的就可以豁免。**

## 退出码：它们实际上意味着什么

实测，不是从手册抄的。

| 工具 | 情形 | 退出码 |
|---|---|---|
| `pngcheck` | 干净 PNG | 0 |
| `pngcheck` | 带追加数据的 PNG | **2** |
| `steghide extract -q` | 密码正确 | 0 |
| `steghide extract -q` | 密码错误 | 1 |
| `steghide extract -q` | 干净载体，任意密码 | **1** |

这里有两个陷阱。

`pngcheck` 对**任何**结构问题都返回 2。追加数据、CRC 错误、文件真的损坏，产生的是同一个码。
一个按退出状态分支的脚本，学到的是「有问题」而不是「什么问题」。要么解析消息，要么用 A 组
模块——它们**被写出来就是为了区分这些情形**。

`steghide` 对「密码错误」**和**「载体里什么都没有」都返回 1。这是「密码不对」与「没有载荷」
之间的差别，而退出码不携带它。携带它的是：成功时输出文件被创建，失败时不被创建。**检查文件，
不要检查退出码。**

## 无法报告「自己没做什么」的工具

最危险的输出，是一个从未检查过你所关心之物的工具给出的干净运行结果。

**`zsteg`** 覆盖 PNG 与 BMP 的 LSB，遍历各种位序与通道组合。它是 LSB **replacement** 的好
分流工具。它对 LSB **matching** 无话可说——**而且它不会说自己无话可说**。一次对携带 matching
载荷的载体的安静 zsteg 运行，是一次「正确执行、无发现」，读起来与「对干净文件的正确执行」
完全一样。T5 量出了 matching 真正需要什么：一个训练过的分类器，真实载体上 `P_E` 0.125，
而结构检测器是 0.405。

**`steghide`** 检测的是 steghide。那是关于一个程序的陈述，不是关于一个载体的陈述。一个
steghide 阴性的 JPEG 可以装着 Jsteg、F5、nsF5 或一个被追加的压缩包。

**`exiftool`** 解析它认识的元数据容器。一个藏在「非文本类私有 PNG 块」里的载荷，或藏在
exiftool 未建模的 JPEG APPn 段里的载荷，既不产生输出也不产生警告。Lab 03 与 Lab 04 之所以
是两个模块，正因为元数据分流与结构记账是两种不同的操作。

**`binwalk`** 找的是内嵌文件签名。在本仓库干净的合成 JPEG 上它报告零行——这是好的情形；而在
真实照片上它经常产出假线索，因为一个签名只有四个字节，而图像里有大量四字节序列。**每一个
binwalk 命中都要先对着容器自身的结构核对偏移**，然后才有意义。

## 清洗载体与读取载体不是一回事

`exiftool -all=` 会移除 exiftool 理解的那些元数据块。在一个把载荷放在 `tEXt` 块里的 PNG 上
实测：lab 03 的检测器**之前报 E1、之后报 E0**，文件缩小 48 字节。**证据没了。**

对一个清洗工具来说这个结果是正确的，而在检验现场这是灾难性的习惯。这里每一条会修改文件的
命令都属于**副本**，而检查清单的第一条——动手之前先对原件做哈希——存在的理由正是这个。

关于这个测量是怎么做出来的，值得说一句，因为**第一次尝试是错的**。去文件里找载荷**字符串**，
在 `-all=` 之前和之后都找不到——因为 lab 03 会对它嵌入的东西编码。于是那次检查「确认」了一个
它从未检验过的论断。**在不知道编码方式的前提下用原始字节搜索载荷，在任何方向上都证明不了
东西。** 检测器才是仪器；`grep` 不是。

## 工具彼此矛盾时，谁是对的

交叉验证真的撞出过矛盾。每一次都是靠找到一个**两个实现都影响不了的第三方参照**来裁决的。

**`djpeg` 的措辞不可移植。** IJG 的 djpeg 与 libjpeg-turbo 的 djpeg 对同一个文件打印不同的
verbose 文本。一个按某个实现的措辞去 grep 的检查会把一个工作正常的工具报成坏的——这在 Kali
上真的发生了，也是 `scripts/verify-toolchain.sh` 现在改为「解码一个文件并检查结果」而不是
匹配字符串的原因。

**两个实现互相一致，在它们共享同一个假设时什么也证明不了。** 本仓库的基线与渐进式 JPEG 解码器
曾经互相一致而**双双错误**，编码器往返测试也通过了，因为编码与解码共享同一个错误。裁决它的是
**从解出的像素直接算 DC 系数**——一个两个解码器都影响不了的参照。当两个工具一致时，问一句：
它们有没有可能一起错。

**原始字符串搜索会漏掉明明存在的载荷。** NTFS 把 MFT 记录内每个 512 字节扇区的最后两个字节
替换成更新序列号。跨越扇区边界的驻留备用数据流因此在原始镜像里是断的、经驱动读则完好：实测，
一个 480 字节的流匹配了 414 字节后中断。**在磁盘镜像上 `grep` 不是一个可靠的内容检验。**

## 操作顺序

检查清单里有完整版；工具层面的版本很短。

1. **对原件做哈希。** 此后一切都在副本上进行。
2. **结构记账**，它是确定性的：每个字节都有存在的理由吗？`pngcheck -v`、
   `djpeg -verbose -verbose`、`unzip -l`、`binwalk`，外加 A 组模块补上它们漏掉的情形。
3. **元数据**，它是独立的一步：`exiftool -a -G1 -s`。
4. **然后才是信号层分流**，它需要阈值，而阈值需要在同源干净载体上实测的基线。

**先跑第 4 步是得到「自信的错误答案」最常见的方式**，因为统计检测器总会返回一个数字。

## 需要写进报告的东西

报告里出现的每一次工具调用：工具名、**版本**、确切参数、以及它检查了什么。`steghide 0.5.1`
与 `steghide 0.6` 是不同的程序。`binwalk` 在大版本之间改过输出格式。**一个无法从报告中复现的
发现不是发现。**

以及记录**没有**运行什么。覆盖缺失不等于风险缺失，而一份不说自己跳过了什么的报告，等于在暗示
它什么都没跳过。
