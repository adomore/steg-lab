# T7 -- 取证工作流与决策

> Gate：**G7** -- `python3 gates/g7_capstone.py` -- 已通过

## 7.1 工作流就是提问的顺序

到这里之前的一切产出的是检测器。T7 讲的是它们运行的顺序，以及「在前提未满足之前不回答问题」
这条纪律。

1. **先做结构记账**，因为它是确定性的。每个字节要么有存在的理由要么没有；不需要任何阈值，
   而一次命中产出的是载荷而不是概率。
2. **然后才是统计估计**，它需要阈值，而阈值需要基线。
3. **基线是在记录任何判定之前、在同源干净载体上量出来的**，不是事后拿来为判定找理由的。

## 7.2 把流水线做成可执行的

`steganalysis.pipeline` 就是把那个顺序写下来，好让它能跑在一个没人告诉过它答案的载体上。它接受
字节、一个标签和一组基线。它没有任何参数能让真值传进来——这一点是**结构性检查**的而不是靠信任：
一个**能够**泄露答案的接口，最终一定会泄露。

某一级抛异常时记为「该级失败」而不是中止整个分析——一个能弄坏某个解析器的载体，恰恰是其他解析器
应该看一眼的载体——但失败必须被报告，因为「JPEG 级崩了」和「JPEG 级什么也没找到」是两个不同的事实。

## 7.3 按载体派发不是优化

G7 第一次运行就在「不得过度断言」这条判据上失败：七个干净载体里有三个被报到 E3，而且**全部**在
`jpeg-dct` 域。

原因不在某个检测器。是每一个统计检测器都跑在了每一个载体上，于是 lab 14 的工作点——在质量 90 的
**灰度** JPEG 上量的——被套到了彩色 JPEG 上，而 lab 07 在灰度 PNG 上量的工作点被套到了一切东西上。

**阈值是载体的属性。** T4 第 4.7 节量到这个错误把误报率从 0% 推到 25%，T5 第 5.6 节量到分类器从
P_E 0.140 掉到随机水平。流水线自己正在犯这门课程存在的意义所要警告的那个错。

所以流水线现在按容器类型派发，并且拒绝把灰度校准的阈值用到彩色载体上——判断依据是解析 `IHDR`
的颜色类型或 SOF 的分量数，不是文件名。过度断言从三个变成零，准确率从 0.90 变成 1.00。
**拒绝运行某个检测器，也是一种结果。**

## 7.4 收官测试量出了什么

30 次试验，答案封存，7 个干净、23 个携带，横跨五种配方与四个域。

| | 判为干净 | 判为携带 |
|---|---|---|
| **干净** | 7 | 0 |
| **携带** | 0 | 23 |

域命名正确：23/23。没有任何一级在任何载体上失败。

那个准确率数字是里面最不重要的东西。**要紧的是哪一格是空的。**

## 7.5 两种错误的代价不相等

判据 C——零个干净载体被报到 E3 或以上——与准确率**分开评分**，而且它单独一条就能让整道 gate 失败。

漏掉一个载荷，代价是一条调查线索。做出一次虚假确认，代价是某个人的辩护。一次「漏掉一半载荷但从不
过度断言」的运行能通过判据 C；一次「全部抓到但过度断言了一次」的运行不能。

这也是为什么 P_E——这个领域的标准指标，它给虚警与漏检同等权重——对论文里比较方法是正确的默认，
对任何真实案件都是错的默认。第 5.4 节从另一头讲了同一件事。

## 7.6 报告可以说什么、不可以说什么

检查清单里都有；这里重复三条，因为它们最容易丢。

**级别、检测器、阈值、基线要一起写出来。** 不附基线的数字不算结果。证据阶梯把这一条做成了机械的：
`assert_reportable()` 是抛异常而不是发警告，所以一条没有实测基线和已识别域的 E3 发现根本无法被记录。

**「未发现载荷」不等于「不存在载荷」。** 主动信道可能已经摧毁了一个。Gate G0 量到质量 90 的 JPEG
重压缩把 LSB 载荷的误码率推到 0.498、把 steghide 提取推到 12/12 失败。要说清检验的是哪一种。

**记录没有检验的部分。** 覆盖缺失不等于风险缺失，而一份不说自己跳过了什么的报告等于在暗示它什么都
没跳过。本仓库在不对来源训练分类器的前提下检测不了 LSB matching（T5）、无法在 F5 与 nsF5 之间点名
（lab 14）、对调色板与音频载体完全没有检测器。

## 7.7 延伸阅读

NIST SP 800-86 论把取证技术整合进事件响应；ISO/IEC 27037 与 27042 论数字证据的识别、保全与解释；
SWGDE 的图像分析指南；以及 Daubert 标准——正是它让「你的错误率是多少」成为你会在宣誓下被问到的
问题，也是证据阶梯要求实测基线而非貌似合理的基线的原因。
