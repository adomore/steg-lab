# T1 -- 载体与嵌入域

> Gate：**G1** -- `python3 gates/g1_parsers.py` -- 已通过

## 1.1 载荷可以住在哪里

每一种载体都提供三类性质不同的空间，它们需要不同的工具：

| 层 | 空间来自 | 检测手段 | 对应模块 |
|---|---|---|---|
| 容器层 | 解码器忽略的语法 | 结构记账 | A 组（01-06） |
| 信号层 | 采样值中的感知冗余 | 统计 | B、C、D 组 |
| 语义层 | 格式留给编码器的自由选择 | 对编码器建模 | C 组、T5 |

本课程从容器层开始，有两个理由。一是现实世界中的隐写大多确实住在这一层——恶意软件
投放器与 CTF 题目皆然；二是这一层的推理是确定性的，分析员可以先把记账习惯练出来，
再去面对统计。

## 1.2 容器层，逐格式看

**PNG** 是块流：`length | type | data | crc`。四个属性位藏在四个类型字母的**大小写**
里，而顺序正是坑人的地方：

| 字母 | 小写表示 |
|---|---|
| 1 | 辅助块 -- 解码器可以跳过 |
| 2 | 私有块 -- 未在注册表中 |
| 3 | 必须**大写**（保留位） |
| 4 | 在无关编辑中可安全复制 |

私有位是第 2 个字母，不是第 3 个。本仓库自己的解析器一直搞错，直到 gate G1 的偏移
检查在一个「位置定位正确但分类错误」的块上失败。

PNG 的空间：未知块类型、超长文本块、陈旧 CRC、`IEND` 之后的数据，以及声明行数少于
`IDAT` 实际内容的 `IHDR`。

**JPEG** 是标记流。段带两字节长度字段，而熵编码扫描没有。扫描内部的字面量 `0xFF`
以 `0xFF 0x00` 存储，只有第二字节非零且非 `RSTn` 才终止扫描。

那个缺失的长度字段是重要的不对称。它正是为什么字节记账——本层其他场合的主力——
无法检测追加在扫描后的填充，也是为什么 lab 06 需要的是一个 Huffman 解码器而不是
解析器。1.5 节展开这一点。

JPEG 的空间：`COM` 段、异常 `APPn` 槽位、`EOI` 之后的数据，以及扫描后填充。

**ZIP** 是从中央目录结束记录倒着读的，因此凡是中央目录不愿提及的，都是按设计不可见。
空间：压缩包注释、条目之间的缝隙、extra field，以及那个声称加密却什么也不提供的
通用位标志。

## 1.3 信号层，一页概览

细节属于 T2-T6，这里只放地图。

**空域。** 像素值，通常 8 位。LSB replacement 直接写入比特，LSB matching 则加一或
减一。这两者听起来相似，实则不然：replacement 在偶数值与奇数值之间引入了结构性的
不对称，RS 分析与 Sample Pair Analysis 正是利用这一点；matching 不引入，这也是那些
检测器在它面前崩溃的原因。T4 会把这个崩溃**量出来**，而不是描述它。

**JPEG DCT 域。** 对象是量化后的系数，不是像素。Jsteg、OutGuess、F5 与 steghide
都住在这里，各自留下不同的指纹：直方图形状、量化表选择、标记段布局。仅凭量化表往往
就足以识别生成软件。

**调色板。** GIF 与 8 位 PNG。载荷可以进像素索引，也可以进调色板的排序——EzStego
做的正是后者。

**音频、视频、文本、网络。** WAV LSB 与回声隐藏；运动矢量与容器附件；零宽字符与
变体选择符；协议头字段、DNS 标签与包间时序。D 组，P3 阶段。

## 1.4 统摄一切的那个数：每元素比特数

单说载荷大小没有意义。可比较的量是**相对载荷**，空域用每像素比特（bpp），JPEG 用
每非零 AC 系数比特（bpnzac）。

之所以重要，是因为检测器性能是相对载荷的函数，而不是绝对大小的函数。同样 10 KB 的
载荷，在 128x128 的载体里唾手可得，在两千四百万像素的载体里几乎不可见。T4 与 T5 的
每一条 ROC 曲线都以这个量为横轴，不附带它的结果不算结果。

## 1.5 Gate G1：不用解码器做解析

主张是：载体的结构可以仅从字节流中复原。这个主张的风险在于自欺——很容易写出一个
与自己的心智模型一致、却与现实不一致的解析器。所以这道 gate 用两个并非为本仓库而写
的实现来给手写解析器打分。

### 判据 A -- PNG 对 pngcheck

50 个载体，**比对 162 个 chunk**，在块类型、文件偏移、声明长度上零容忍，另加尺寸、
位深与隔行标志。

**分歧：0。**

有一个细节值得记下来，否则要浪费一个下午：`pngcheck` 报告的是四字节**类型**字段的
偏移，而本解析器报告的是它前面那个**长度**字段的偏移。换算关系是
`pngcheck_offset = parser_offset + 4`。

### 判据 B -- JPEG 对 djpeg

50 个载体、五档质量因子，去 zigzag 还原为自然序后**比对 100 张量化表**，另加帧尺寸
与分量数。

**分歧：0。**

libjpeg 在 `jpeg_read_header` 之后按自然光栅序存储量化表，而 `DQT` 段是按 zigzag 序
存储的。不套用 `jpeg_natural_order` 直接比对，每张表会产生 64 处虚假差异，以及非常
困惑的一个小时。

### 判据 C -- 偏移定位

三个载荷偏移已知的载体：追加在 `IEND` 之后、`IEND` 之前的私有 `stEG` 块、`SOI`
之后的 `COM` 段。每个偏移都必须被精确报出，且每个文件的每一个字节都要能被记账。

**三条全过**——但那是在 1.2 节那个属性位 bug 被修掉之后。这道 gate 在它本来要验证的
代码里找出了一个真实缺陷，这是设立它的最好论据。

## 1.6 这一章真正要教的习惯

在动用任何统计之前，按顺序问三个问题：

1. **容器能解析吗？** 错误是发现，不是异常。
2. **每个字节都属于某个东西吗？** 把结构求和，与文件长度比对。
3. **格式对自己的两份描述一致吗？** 本地头对中央目录；`IHDR` 对解压后的 `IDAT`；
   声明的扫描对解码出来的扫描。

第 3 问是 A 组大部分内容的一般形式，而且在更高层依然有效。

## 1.7 延伸阅读

PNG 规范（ISO/IEC 15948）与 JPEG 的 ITU-T T.81，两份都值得读原文。`pngcheck` 与
libjpeg 的 `djpeg` 源码是本章据以打分的参考实现。信号层地图见 Fridrich (2009) 第 4 章。
