# Lab 23 -- 文件 slack：载荷不跟着文件走

| | |
|---|---|
| 嵌入域 | filesystem |
| 算法族 | file-slack |
| 检测器 | `fat_file_slack` |
| 实测误报率 | 全新格式化卷上 0/8 |
| 检出 | 8/8；载荷逐字节复原 |
| 证据上限 | E4 |

## Slack 是什么

文件系统按**簇**分配存储。一个 N 字节的文件在簇大小为 C 的卷上，会在最后一个簇里留下
`C - (N mod C)` 个字节——它们属于该文件的分配，却不承载它的任何内容。在 16 MB FAT16、
簇 4,096 字节的卷上实测：

| 文件 | 大小 | 簇数 | slack |
|---|---|---|---|
| A.TXT | 11 | 1 | 4,085 |
| B.BIN | 5,000 | 2 | 3,192 |
| C.DAT | 8,192 | 2 | **0** —— 恰好整簇 |

## 当载体是「卷」时，什么变了

之前每一种载体都是文件的一部分。复制文件，载荷就跟着走。

**slack 是卷的属性。** 把文件复制出来，载荷留在原地；做一次碎片整理，它就移位或消失。这一个
事实重排了整个检验流程：**证据是磁盘镜像，而一份文件的工作副本不是证据的副本。** 一个只收集
文件、没有做卷镜像的检验人员，在毫不知情的情况下已经摧毁了这条信道。

## 那个孪生兄弟，而且它并不罕见

之前每个模块问的都是「这个异常是不是载荷」。而在这里，非零的 slack 有第二种解释，它不只是
「有可能」，而是**正常现象**。

删掉一个文件，让一个更小的文件占用它的簇，旧文件的尾巴就活在新文件的 slack 里。构造并实测：

```
BIG.DAT  = "CONFIDENTIAL MEMO " x 220     -> written, then deleted
NEW.TXT  = "short\n"                      -> takes the same cluster
```

检测器报告 3,954 个非零 slack 字节、3.5 bits/byte，而提取出来的内容是：

```
ENTIAL MEMO CONFIDENTIAL MEMO CONFIDENTI
```

**刻意放置的载荷与被删文件的尾巴，产生完全相同的发现。** 这里没有任何统计量能区分它们，而
硬造一个会比承认它更糟：熵不行，因为两者都可能是文本、也都可能是压缩数据；位置不行，因为两者
都从 slack 的开头开始。

所以检测器报告这个发现，并在自己的 claim 文本里**把两种读法都写出来**。由分析员读取复原的字节
并作判断——这是正确的分工。而且值得注意：**那个无辜的解释往往是更有价值的证据。** 对多数调查
而言，复原一份被删除的机密备忘录的尾巴，比证明某人用了隐写更要紧。

## 为什么这里的基线格外强

`mkfs.vfat` 会把簇清零，所以全新格式化的卷上非零 slack 为零——在 8 个新卷上实测每个文件都是 0
字节。这让误报率在**全新卷上**真的是零，也让那个限定词变得关键：在一个用过的卷上，基线是删除
历史留下的东西，而那不是零。

## 为什么选 FAT，以及还缺什么

选 FAT 是因为整条链条都能在本仓库内部验证：`mkfs.vfat` 建卷、`mcopy` 写入、`fsck.vfat` 与
`mdir` 核对——于是几何参数、目录项与文件大小全都是对着独立工具测的，而不是对着本解析器自己的
假设。

ext4 的 slack 与 NTFS 的备用数据流需要挂载卷和本环境没有的权限。它们**继续登记为缺口**，而不是
被近似掉——因为一个无法验证自己的模块比没有模块更糟。

## 它教什么

在问「里面有什么」之前，先问**载体是什么**。这里的载体不是那个看起来藏着载荷的文件——是卷；
