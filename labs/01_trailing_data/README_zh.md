# Lab 01 -- 追加在文件结构末尾之后的数据

| | |
|---|---|
| 嵌入域 | container |
| 算法族 | append-after-terminator |
| 检测器 | `trailing_data` |
| 实测误报率 | 同源干净载体 0/100 |
| 证据上限 | E4（载荷已到手） |

## 手法

PNG 到 `IEND` 为止，JPEG 到 `EOI` 为止，GIF 到 `0x3B` 为止。三种解码器都不关心
后面还有什么，于是直接拼接就是一个可用的载体：

```bash
cat cover.png payload.zip > carrier.png
```

产物在任何看图工具里都能打开，渲染结果完全一致，而且能携带任意长度的数据。

## 为什么它一直有效

主流解码器都是按「宽容」写的。一个在终止符之前合法的文件就是合法文件；对终止符
之后的字节报错，误伤的正常图片会远多于抓到的隐写。这份宽容是有意为之、是正确的，
也因此是永久可利用的。

## 检测

这里没有算法，这恰恰是重点。让这个检查可靠的是一套记账纪律：

1. 结构化解析容器。
2. 算出它在哪个偏移结束。
3. 与文件长度比对。
4. 把每一个无法解释的字节都当作「需要一个名字」的东西。

对像素做统计的检测器完全看不见这一类——因为这些字节根本不在图像里。

## 它教什么

面对一个载体，第一个问题不是「这看起来像什么」，而是「这个文件里每一个字节，是否
都有结构上存在的理由」。A 组的大部分内容，就是把这个问题在不同容器里各问一遍。
