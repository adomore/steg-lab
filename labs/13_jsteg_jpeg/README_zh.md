# Lab 13 -- JPEG DCT 域中的 Jsteg

| | |
|---|---|
| 嵌入域 | jpeg-dct |
| 算法族 | jsteg |
| 检测器 | `jsteg_pair_chi_square`（滑窗） |
| 实测误报率 | 同源干净 JPEG 上 0/30 |
| 检出 | 200 到 1100 字节各载荷均 10/10 |
| 证据上限 | **E4** —— 载荷逐字节复原 |

## 为什么这个模块之前不可能存在

缺口 G-14。`decode_scan` 从 P0 起就能产出 DCT 系数，但没有任何东西能把改动后的系数写回
一个合法 JPEG，于是 JPEG 域的模块无物可检。`steganalysis.jpeg_encode` 关掉了这一点：
它用实际出现的符号重建霍夫曼表来重写熵编码流，往返被验证为系数级逐位一致。

重建表不是优化。改动一个系数可能改变它的幅值类别，产生源文件的表里从未包含的
`(run, size)` 符号——所以复用原表恰恰会在嵌入器制造出来的那些输入上失败。

## 统计域里的第一个 E4

Lab 07 与 09 止步于 E3：它们确认了载荷存在，却拿不出载荷，因为嵌入路径是带密钥的。

Jsteg 顺序地写入每一个幅值大于 1 的系数。顺序由算法固定，因此提取不需要密钥。域是
统计的，路径是确定的，载荷逐字节出来。

## 检测：这个攻击的原始形态

全局卡方在载荷只占一部分时会失败——未被触碰的尾部保留着自然的不平衡，把和淹没了。
Westfeld 与 Pfitzmann 的攻击改为沿着 Jsteg 自己的写入顺序滑窗，既能检测**又能测量**：

| 真实载荷 | 检出 | 估计长度 |
|---|---|---|
| 200 字节 | 10/10 | 243 |
| 400 字节 | 10/10 | 396 |
| 800 字节 | 10/10 | 793 |
| 1100 字节 | 10/10 | 1152 |

干净载体：30 张里 0 次误报。

## 阈值是量出来的，不是引用来的

教科书上「被抹平」的数字是 p 值接近 1。在这个载体上，那会漏掉每一个小于约 1200 字节的
载荷。

实测的是：30 张干净载体上窗口 p 值的最大值为 0.277（均值 0.124），而嵌入窗口落在 0.5
到 0.99 之间。工作点取 0.40——高于观测到的干净上限并留有余量，远低于嵌入区间。它是这个
载体的属性，换任何来源都必须重新测。

## 这个模块暴露出的两个 bug

**Jsteg 跳过的是幅值，不是值。** P1 的嵌入器排除的是等于 0 和 1 的系数，放过了 -1。
把比特 0 写进 -1 会得到 0，这会把该系数从提取路径上抹掉，之后每一位都失步。在修掉它
之前，提取在第 1 个字节就出错——嵌入器与本模块两处都改了。

**负数对是镜像的，不是平移的。** 幅值 2 与 3 配对，所以 -2 与 -3 配对。把 -2 和 -1
配成一对，等于把一个碰不到的值放进了检验：-1 保持它的自然计数，而 -2 被拿去和「没有
东西」做平衡，于是统计量在每个窗口上都报 0.000，包括完全嵌入的窗口。在修正镜像之前，
这个检测器看上去是死的。

两个 bug 都是靠把模块做出来发现的，不是靠读代码发现的。

## 复现

```bash
python3 -m pytest tests/test_labs_d.py -q
python3 scripts/verify-jpeg-encoder.py
```

## 它教什么

一条确定的嵌入路径给分析员带来的好处，大于一个弱算法给嵌入方带来的好处。Jsteg 的跳过
规则本是为了避免显眼的改动，结果既造出了识别该工具的指纹，又交出了固定的顺序、连带交出
了载荷。
