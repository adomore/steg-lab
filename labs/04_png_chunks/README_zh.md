# Lab 04 -- PNG 块级异常，以及那个把像素藏在明处的手法

| | |
|---|---|
| 嵌入域 | container |
| 算法族 | private-chunk / stale-crc / header-truncation |
| 检测器 | `png_unknown_chunk`、`png_crc_mismatch`、`png_height_truncation` |
| 实测误报率 | 同源干净载体 0/100 |
| 证据上限 | 私有块与高度截断 E4，陈旧 CRC E2 |

## 三个变体，三种不同的失效方式

**(a) 私有块。** 结构上完美无缺、只是类型没人注册过的块。长度正确、CRC 有效、
属性位正确。唯一的发现途径是追问每个块「是干什么用的」。

**(b) 陈旧 CRC。** 把载荷覆写进已有块的数据区，但不修校验和。没有看图工具会校验
块 CRC，所以图片照常显示。

**(c) 高度截断。** `IHDR` 声明的行数少于 `IDAT` 流里实际包含的行数。所有看图工具
都会渲染声明出来的那张图，然后默默丢掉剩下的部分。

## 为什么 (c) 才是必须内化的那个

没有追加，没有位置错乱，每个 CRC 都有效。这是一个完全合法的 PNG，任何一致性检查
工具都会放行。

载荷是被一个**声明**藏起来的，不是被一种编码藏起来的。于是：

- 追加数据检查什么都看不到（`trailing == b""`）
- CRC 校验什么都看不到（全部有效）
- 熵扫描什么都看不到（那就是普通的压缩像素数据）
- 像素统计什么都看不到（隐藏的行根本没被解码）

唯一能找到它的检查，是把 `IDAT` 解压后与文件头蕴含的长度做比对。测试把上面这几条
逐条断言了，所以这是被验证过的结论，不是一句主张。

## 属性位陷阱

PNG 用四个类型字母的**大小写**编码四个标志位：

| 字母 | 小写表示 |
|---|---|
| 1 | 辅助块（ancillary） |
| 2 | 私有块（private）—— **不是第 3 个字母** |
| 3 | 必须大写（保留位） |
| 4 | 可安全复制 |

本仓库的参考实现一直把第 2、3 个字母搞反，直到 gate G1 抓到。同一条测试现在在
Python 与 Rust 两侧都有。
