# Lab 03 -- 把元数据当载体

| | |
|---|---|
| 嵌入域 | metadata |
| 算法族 | text-chunk / comment-segment payload |
| 检测器 | `metadata_profile` |
| 实测误报率 | 同源干净载体 PNG 0/100、JPEG 0/100 |
| 证据上限 | 字段可解码时 E4，仅「看着不对」时 E2 |

## 手法

元数据是一处设计之初就存在、被标准祝福、且实际上没有长度上限的地方，用来存放没有
任何解码器校验、也没有任何看图工具显示的字节。PNG 提供 `tEXt`、`zTXt`、`iTXt`；
JPEG 提供 `COM` 和十六个 `APPn` 槽位。两者在多数复制、上传、缩放操作中都原样存活。

`zTXt` 尤其有意思：载荷入库前先做 deflate，于是朴素的字符串搜索什么也找不到，而
熵扫描在本该是图片说明的地方看到的是压缩噪声。

## 为什么误报率就是全部问题

每张真实照片都带元数据，相机会写进去好几 KB。所以「这个文件有元数据」毫无价值，
真正有用的陈述是「这个文件的元数据，不像这个来源会产生的元数据」。

这是一个关于**来源**的断言，也就意味着不先刻画来源就说不出口。建立在错误的相机、
错误的导出流水线、错误的社交平台上的画像，不算画像。

## 检测

三个信号叠加：

- 长度超出一条图片说明合理需要的范围
- 熵高于散文能达到的水平（任意字节的 base64 落在约 6.0 bit/byte，英文文本约 4.2）
- 字段能干净地按 base64 解码

只有第三条能给到 E4，因为只有第三条产出了载荷。
