# Lab 10 -- 调色板载体：藏在一个顺序里

| | |
|---|---|
| 嵌入域 | palette |
| 算法族 | ezstego |
| 检测器 | `palette_sorted_pair_chi_square`（滑窗） |
| 实测误报率 | 同源干净调色板 PNG 上 0/24 |
| 检出 | 800 与 1500 字节各 10/10；300 字节 0/10 |
| 证据上限 | E4 —— 顺序可从文件本身导出 |

## 两个藏身处，其中一个行不通

调色板图像存的是索引，不是颜色。

**索引的 LSB** 是显然的目标，而且没用。调色板顺序是任意的——量化器按自己算法到达颜色的先后
输出——所以翻转索引的低位，等于把一个像素换成一个不相干的颜色。破坏是肉眼可见的。

**EzStego** 不再把索引当成一个数，而是当成**排序后**顺序里的一个位置。按亮度排序之后，位置
2k 与 2k+1 指向亮度相邻的颜色，在两者之间移动几乎不可见。载荷就住在「亮度排序位置」的 LSB 里。

## 手法本身就是破绽

按亮度排序把调色板变成一串近乎重复的对，而嵌入会把每一对内部的计数抹平。这与卡方攻击在空域
里找的是同一种结构，只是施加在排序位置上而不是像素值上。

在原始索引上工作的检测器什么也看不到，因为原始的对毫无意义。而重建了排序顺序的检测器立刻就
看到了——并且它能精确重建，因为**调色板就装在文件里**。

## 不需要密钥，所以这里能到 E4

Lab 07 与 09 都停在 E3：确认了载荷却拿不出来，因为嵌入路径是带密钥的。EzStego 的路径不是。
顺序是调色板的函数，调色板在文件里，写入顺序是顺序的。载荷逐字节出来，10/10。

## 滑窗，理由和 Lab 13 一样

192×192 载体里的 300 字节载荷只碰到 6.5% 的像素，全局统计量纹丝不动。沿 EzStego 自己的写入
顺序滑窗，就能找到前端那一串被抹平的窗口：

| 载荷 | 检出 | 估计 |
|---|---|---|
| 300 字节 | 0/10 | -- |
| 800 字节 | 10/10 | 512 |
| 1500 字节 | 10/10 | 1382 |

300 字节这次漏检不是调参不到位。2400 比特不到一个 4096 采样窗口的三分之二，所以**没有任何一个
窗口被填满过**。窗口大小就是检测下限，而缩小窗口是拿这个下限去换每个窗口内的计数噪声。这一点
写出来而不是藏起来。

干净载体：24 张的窗口 p 峰值全为 0.0000，而工作点是 0.60。

## 复现

```bash
python3 -m pytest tests/test_labs_e.py -q
```

## 它教什么

隐写不需要一个数值来藏身。它需要的是格式留下的任何一个不受约束的自由度，而调色板的顺序就是
一个。检测器的工作，是找到让那个自由度变成统计量的那个框架——在这里，是一次排序。
